Design & implementation plan

rongo

Understanding code without going through a person first. The question is asked in your own words, the answer comes at the altitude you picked — business analyst or developer — and every sentence is sourced.

Why

Anyone who wants to know how teaser mail sending is implemented has to interrupt a developer today, and gets an answer at the wrong altitude. rongo removes that dependency: it indexes the repositories, asks back which mechanism is meant, and explains it at the level chosen up front — business analyst (BA) or developer (DEV). Every statement stays checkable through an expandable source panel.

Name

The product is called rongo — in the interface, in the module path, in the binary, in the container. Named after Rongorongo, the never-deciphered Rapa Nui script written in boustrophedon (the reading direction alternating line by line, like a mechanism that jumps back and forth between layers). «Rongorongo» is etymology only and must never appear as a product name. The boustrophedon stays a story and is not translated into the interface — see the decision under «Interface».

Constraints

  • Architecture from ../peeq: one static Go binary, an embedded React SPA, one SQLite file, one container.
  • Xiaomi MiMo Pro and non-Pro for generation, OpenAI for embeddings. Both external — source code leaves the network.
  • 20–200 repositories, one internal server, a small team. Admin token now, OIDC later.
  • Answers in English.
  • Only the final answer is streamed. Every internal step is an ordinary request.
  • Token and cost accounting, prices from the litellm catalogue. Reported in USD — the catalogue is in USD, which removes every conversion and every exchange rate.

Careful when copying

The versions come from peeq/backend/Containerfile and go.mod, not from peeq/AGENTS.md — that one is stale and still names Go 1.25 and debian:12-slim. Do not «correct» this plan against it.

Runtime image debian:13-slim, not distroless: rongo calls git, rg and ctags as external programs. All three are new here. That is exactly what keeps CGO_ENABLED=0 alive — Go bindings for tree-sitter need cgo, an external symbol extractor does not.

SQLite and sqlite-vec are one unit

The vector bindings are not an independent package but a wasm build compiled against ncruces' SQLite. Version skew therefore does not break compilation, it breaks vector search — in the worst case as an empty result list in production. peeq and loom both run on the same pair:

ModuleVersionWhy exactly this one
ncruces/go-sqlite3v0.23.3Carries the wasm runtime the extension is loaded into.
asg017/sqlite-vec-go-bindingsv0.1.7-alpha.2Built against exactly that runtime. Alpha — read the changelog before every bump.
  • Bump both together or neither. A lone Dependabot bump is precisely the case that breaks this — which is why the two later have to go into one grouped PR.
  • Stay on the same pair as peeq and loom. Diverging means a fix found there no longer carries over here.
The pin alone does not protect anything

It only moves the problem to the day of the bump. What protects is a test that actually drives vec0: create the table, insert a vector, run a KNN query, check the neighbour. That turns a silent runtime break into a red CI. This test belongs in phase 1, together with the migration runner — not in phase 2 when search is built.

Models — where Pro, where non-Pro

The yardstick is peeq's rule: what a human reads runs on Pro. What is an id, a label or an intermediate result runs on non-Pro with ShortGate — the smaller queue, not «the model without thinking». Both are reasoning models; WithoutThinking and ShortGate stay separate switches.

Call siteModelReason
Understandnon-ProThe result is JSON: intent, search terms, repo hints. Nobody reads it.
RouteProThe result is module ids and a threshold decision — one word, but it decides answer versus follow-up question. The one measured exception, see docs/measurements/2026-08-19-candidates.md.
Gather / relevancenon-ProThe highest-volume place: many iterations per question, each answering «follow, yes or no». This is where the money is.
Thread titlenon-ProIt is on the page, but it is a label of a few words — hence non-Pro, deliberately and not by accident. Runs alongside the answer and must never hold it up.

Pro therefore runs exactly once per question. Every call gets an upper bound through llm.WithMaxTokens, unless a truncated reply would be worse than a long one.

The place where saving costs quality

Routing decides whether the right code is found at all. If non-Pro routes wrongly, Pro then writes a convincing wrong answer — the most expensive kind of failure this product can have. That is why phase 4 measures the hit rate of routing against Pro over a fixed question catalogue before non-Pro is written in there. Asserting it is not enough.

Embeddings

OpenAI text-embedding-3-small, 1536 dimensions. Decided and measured at the end of phase 2: docs/measurements/2026-08-17-embedding-model.md. 28 questions against the dev corpus, each model indexed once. large leads on all three figures (recall@5 0.714 vs 0.679, recall@20 0.857 vs 0.786, MRR 0.538 vs 0.476), but at 28 questions the difference is indistinguishable from noise (McNemar p ≈ 0.63 and 1.0 respectively). On a tie the cheaper and faster option wins: small costs a sixth, needs half the vector storage and indexes the corpus in 450 instead of 675 seconds. Four questions fail on both models — that is a chunking and ranking problem, not an embedding problem.

Repositories — rongo clones them itself

Decision

Not the GitHub contents API. Three reasons, each disqualifying on its own: it cannot grep, single file fetches hit the rate limit at this corpus size, and «why is it like this» needs a local git log.

The repository list lives in a file

No form per repository — at 200 of them that would be 200 forms, and a newly added repository gets forgotten. Instead repos.yaml next to the configuration: name, clone URL, branch, enabled yes/no. Versionable, reviewable, readable in a diff.

The branch per repository

branch: can be given per entry, but is optional — and the default is never master. Omitted means: resolve the remote's default branch (git ls-remote --symref origin HEAD). The dev corpus shows why:

RepositoryDefault branch
peeq, loom, rongomaster
ncruces/go-sqlite3, asg017/sqlite-vecmain

A hardcoded master would therefore break exactly the two third-party repositories the composition logic depends on. The branch is only given when it should be something other than the default — a release branch, say.

One branch per entry, not several

Indexing several branches of the same repository at once would be the obvious thing to do, but it is harmful: it produces candidates that differ only in the branch, and with them a constant stream of follow-up questions with no substance. Anyone who really needs a second branch adds a second entry with its own name (shop-backend@release-2024.3). The branch is then part of the identity and shows up visibly in candidates, sources and answer, instead of as a puzzling doppelganger.

The branch therefore belongs in the source (repo, branch, file, line) and in the forge URL — otherwise a link points at a line that does not exist on the default branch at all.

The dangerous failure

When the configured branch disappears on the remote — a tidied-up release branch — the poller must not stop quietly. Otherwise the index freezes while everything looks healthy, and rongo answers from months-old code. This has to be a loud error on the Repos page.

Changing the branch in the YAML incidentally does not force a full reindex: git diff <last indexed SHA>..<new HEAD> is valid across branch boundaries too, because both live in the same object store.

No credentials in the YAML

The file ends up in a repository or a ticket sooner or later. Tokens therefore live exclusively in BACKEND_* environment variables, one per forge host; the YAML at most names the variable, never its value. A PAT is injected into the remote URL at fetch time and never logged.

  • Read at startup, plus an admin button «reload the list» — the compromise «a change needs a deploy» otherwise costs a restart for nothing.
  • Full clone into BACKEND_REPO_ROOT/<name>. The history is needed by the «why» pipeline, and source code is cheap on disk.
  • Refresh: a poller (30 minutes by default, jittered) runs git fetch and compares the HEAD SHA. Unchanged → done. Changed → git diff --name-only and reindex only those paths.
  • When a repository disappears from the list it is deactivated, not deleted: it drops out of search, its index stays. Only an explicit admin command clears it. A typo in the YAML must not destroy hours of indexing.
  • The Repos page is therefore read-only status rather than a maintenance form: last sync, HEAD SHA, number of chunks and modules, errors from the last run.
  • Webhooks stay out — polling needs no ingress and no delivery error handling.

Index — three levels, one file

«I found three teaser mail mechanisms» presupposes named candidates — vectors at chunk level return twenty snippets, not three features. The candidates are not an index level though: they are formed per question from the result list over deterministic module clusters. Only what can be cited is stored.

LevelContentAnswers
chunks + _vec + _ftsCode and documentation chunks, embedded and full-text indexed. Symbol-exact where ctags yields something, otherwise line windows with overlap.The substance of the answer.
repo_depsFrom the dependency manifests: which coordinate a repository publishes and which ones it pulls. Not embedded.Separates composition from ambiguity and carries gathering across repository boundaries.
history_docsCommit messages and PR text as a document type of their own, embedded.«Why is it like this» — that use case costs no more than this.
Decision: no generated description level

rongo never stores or embeds model-written text about code — not per module, not per file, not per symbol. Three reasons, each sufficient on its own:

  • The cost scales with the corpus instead of with usage. 200 repositories with 50 to 150 modules are tens of thousands of Pro calls before anyone has asked a question — and every refactoring that moves module boundaries runs up the bill again.
  • A generated description is structurally stale. It claims something about code instead of showing it. The claim goes quietly wrong, and the answer built on it is convincingly wrong — exactly the kind of failure this product tolerates least.
  • The resolution does not work out. Coarse enough to be cheap means too coarse for concrete questions. Fine enough for concrete questions means the code has been rewritten in prose — more expensive and less precise than the original.

The cheapest precursor of this level was measured as well, and lost; the two addenda at the end record the numbers and the counter-test. What remains is deterministic clustering without a model call, and naming only once a human really sees the candidates.

What exactly the embeddings sit on

Not on raw code. A question in domain language and a method body share almost no words — embedded raw, the vector space finds nothing. What is embedded is therefore an enriched text per unit, while the full-text lane (FTS5) indexes the raw code in parallel. That is precisely the point of hybrid search: PromoMailJob is found literally by the full-text lane, «teaser mail» is found by meaning in the vector lane.

UnitWhat goes into the vectorCut
Code chunk Repo and path breadcrumb, the enclosing symbol names (class, method) from ctags, the doc comment if present, then the body. From one symbol line to the next, capped; beyond that, windows with overlap.
Documentation chunk Heading path plus section text. Already natural language. At headings.
Domain text in the repo Resource bundles and i18n files, mail and page templates, test names — human-written domain language, taken over raw with the repo and path breadcrumb. Bundle entry, template section, test method.
History document Commit subject, body and changed paths; the commits of one PR pulled together into one document. One PR, one document.
Query side Not the raw question, but the expanded one from step 1 — once in domain language, once with guessed code vocabulary; both result lists are merged. —

The bridge between domain and code vocabulary is therefore found rather than generated: «teaser mail» appears literally in the resource bundle, in the mail template and in the test name, and those places are citable and go stale only as the code goes stale. The second half of the bridge sits on the query side — step 1 additionally searches with guessed code vocabulary.

No tree-sitter, no AST

An AST would be the more precise cut, but it costs three times over: cgo (and with it CGO_ENABLED=0), a grammar per language and knowledge of its node names to write a query at all. With a mixed corpus that means understanding the tree first for every new language. ctags yields a uniform record for around 150 languages — name, kind, line, scope — and chunking needs nothing beyond symbol boundaries. Where ctags yields nothing, the line window takes over; that is not an emergency, it is the normal path.

Before embedding, everything that only creates cost is filtered out: vendored dependencies, generated code, lock files, binaries, minified files, and licence headers at the top of a file. Without that filter you pay for megabytes of noise and dilute the result list.

Plus a plain symbols table (file → symbol → line) from ctags, for exact name search and for the reverse walk of impact analysis.

The path of a question

A state machine, not a linear stream. Steps 1 to 3 are ordinary internal calls, only step 4 streams.

1 · Understand
non-Pro, JSON replyIntent (how, why, where, conformance), expanded search terms including guessed code vocabulary, repo hints.
2 · Route
Hybrid search over chunks, grouped by moduleIf the best hit dominates the second by more than BACKEND_ROUTE_MARGIN, it continues quietly. Otherwise: a clarification event with two to five named candidates, and the turn ends. No hit → «nothing found» with the terms that were tried, never an invented answer.
3 · Gather
Chunks, whole files, call chainsWiden hits to whole files, then follow symbol references — bounded to two hops and a token budget. A mechanism spread over controller, service and template is exactly what plain top-k misses.
4 · Answer
Pro, streamedA role-dependent system prompt, in English. Citation markers in the text point at a source list that arrives as an event of its own.

statusclarificationtoken citationsusagedoneerror

The open follow-up question is stored on the thread — the BA's choice arrives as a new request and continues at step 3.

Role choice

audience is ba or dev; in the interface the switch is called BA / DEV and can be set per message. It affects only step 4: level of language, depth, whether code is embedded, whether the source panel starts open. A pleasant consequence: «Explain as Dev» re-runs step 4 alone on the context already gathered — one generation, no new search.

Interface

A single-column thread. Pages: Ask, Repos, Cost, Settings.

  • An input with the role switch right at the field and an optional repo filter.
  • An activity trace after the pattern of loom's ActivityTracePanel: collapsed, a single line with a generated title of what is running, plus chevron and duration. Expanded, a timeline — one clock node per step on a continuous line, closed by a done node with a check. There is one panel per turn, not one per thread — a follow-up question ends the turn and with it the trace. The panel carries role="status" and aria-live="polite" so progress is read out.
  • The trace title is the same non-Pro call as the thread title — it describes the running step, not the question.
  • A trace that runs into a follow-up question does not end on the done check, but on an ochre waiting node («follow-up question asked»). After the choice, a second trace starts with «choice taken». loom does not know this third state — there complete = !active && !streaming, which here would wrongly say «done» while a person is being waited on.
  • The follow-up question as an embedded card, not a dialog window. Every candidate with a title, a repo marker and a one-line summary. While open it is framed in ochre — the colour means «your move».
  • After the choice the card collapses to one line: «Chosen: …» plus the repo marker, and the border goes quiet. It does not disappear — the decision belongs in the record, and sometimes you only notice from the answer that you picked the wrong mechanism. Reopened, every candidate is there with the chosen one marked; another one is clickable and starts a new turn with its own trace and its own answer. Nothing is overwritten.
  • The BA / DEV role switch right at the input field; every answer can be rewritten with «Explain as Dev» without a new search.
  • The answer is streamed, citation markers are superscript, and below them sits a collapsed panel «How does rongo know this?» with repo, file, line and link.
  • Thread title: as soon as the question is sent, the entry is in the sidebar immediately — with the first words of the question, truncated. In parallel non-Pro writes a short title; when it arrives, it quietly replaces the placeholder. The title never waits, and the answer never waits for the title. If the call fails, the placeholder simply stays — that is not a failure anyone needs to see.
  • Everything expandable carries a chevron that rotates 90 degrees downwards on open — no triangle, no plus/minus, no glyph swap. This holds for the source panel and for every later expandable spot.
Decision: no boustrophedon in the interface

Originally the status trace was meant to alternate direction line by line — the motif behind the name, taken literally. With loom's timeline that falls away, and rightly so: the value of the timeline is the continuous line connecting the nodes. Alternating reading direction cuts exactly that line. Readability beats motif.

The alternative would be to spend the motif somewhere it costs nothing — in the empty state, say, or as a margin mark. My recommendation is to drop it: the name already carries the story, and a motif that has to go looking for a place is decoration.

Questions across several repositories

Several well-scoring modules mean two different things, and to a plain score comparison the two look identical:

SituationExampleCorrect reaction
Ambiguity
alternatives		 Three independent teaser mail mechanisms in three products. Ask back. Exactly one module is meant.
Composition
parts of one whole		 The orchestrating service in shop-backend, the shared library in commons-mail, the third-party component behind integration-x. Do not ask back. All three belong in the answer.

A follow-up question in the second situation is not merely annoying, it is substantively wrong: it forces a choice between parts and then produces an answer telling half the truth.

How rongo tells the two apart

Not by the model's judgement alone — there is a hard signal for this. During indexing the dependency manifests are read (pom.xml, build.gradle, package.json, go.mod, requirements.txt, *.csproj) and written into a repo_deps table: who publishes which coordinate, and who pulls it. From that follows immediately:

  • If candidate A depends on candidate B per the manifest, they are not alternatives — then it is composition, without a model having to judge it.
  • If there is no dependency and the candidates differ in their domain topic, it is ambiguity — rongo asks back.
  • Only in the remaining case does the routing model decide, and then with the candidates and the dependency situation in the prompt.

Gathering across repository boundaries

Gathering may cross the boundary, but not blindly: a repository quickly pulls forty dependencies, and their source is almost never the answer. The barrier is therefore two-stage — a symbol is only followed when both hold:

  1. The gathered code really references the symbol — the manifest only says which repo it belongs to, the reference says whether it counts.
  2. The target repository is indexed in rongo.

The same hop budget as within one repository still applies; crossing a repository gets no discount.

The boundary is named, not papered over

If the chain leads into something rongo has not indexed — a third-party library, a vendor SDK, an external service — the answer says so explicitly: «The sending itself happens in vendor-mailer, which is not indexed. rongo sees how it is called and configured, not what it does internally.» That is more valuable to the user than a smooth answer, because it names exactly the place where someone still has to be asked. A plausible invention at that point would be the product's most expensive failure.

What that means for the answer

  • The answer names the orchestration first — who calls whom, in what order — and only then the internals of the individual parts.
  • The trace shows the scope («covers 3 repositories»), so it is visible that more than one place was read.
  • The source panel groups by repository, and the counter names both: sources and repositories.

Follow-up questions

A follow-up question always produces a new answer in the thread. The previous one is never overwritten — it may long since have been forwarded or copied into a ticket. The thread is a record, not a working document.

Whether a new search is needed for it is decided by a cheap check on non-Pro: it gets the follow-up question and an inventory of what was already gathered — file list, symbols, chosen module — and answers with «enough» or «fetch more». That gives three cases:

CaseWhat runsCost
Only the role changes
«Explain as Dev»		 Step 4 alone on the same gathered context. No search, no embedding, the same sources. One Pro call.
Going deeper into the same mechanism
«What happens with several open carts?»		 The check asks for more: targeted gathering within the chosen module, with no new routing and no new follow-up question. The context grows. A non-Pro check, some gathering, one Pro call.
A different mechanism
«And how is it in the newsletter?»		 Leaves the chosen module. It is routed again — and may trigger another follow-up question, with everything that entails. A full run.
Why the check is not optimised away

Without it rongo answers every follow-up question from whatever happens to be in context — and phrases it convincingly, although the decisive file was never read. One call on the cheap model is the price of «I do not know, let me fetch it» being possible at all.

The gathered context grows across the thread and is capped. Eviction is by age, but cited files stay: they carry the source panel of older answers, and a source pointing nowhere is worse than a longer list.

Answer length and passing it on

A BA answer is short by default: the core mechanism in three to five paragraphs. It answers the question and stops. Edge conditions and special cases come through a follow-up question — which is cheap, because the context is already gathered, and costs only one Pro call. The token cap through WithMaxTokens is set accordingly; the DEV register gets more room, because code excerpts sit in the running text there.

Export and share link

  • Markdown export of an answer including its sources — purely local, no new route.
  • Share link after peeq's pattern (internal/sharelink): an opaque token, only its hash stored, its own unauthenticated route.
What a share link gives away

It is the only place where rongo hands something out without a sign-in — and what it hands out is an explanation of company code including file and line references. Three restrictions therefore belong with it: what is shared is one answer, never a whole thread (a thread contains questions that are nobody's business); every link is individually revocable; and every existing link is listed in the admin view, or after half a year nobody knows what is out there.

Cost accounting

A single turn consumes several models: non-Pro for understanding, non-Pro for routing, an embedding for the search query, Pro for the answer. Accounting therefore sits per call, not per message.

LevelWhat is recorded there
llm_callsone row per call: message, step (understand, route, embed, answer, name_candidates), model or deployment, prompt, completion and reasoning tokens, computed cost in USD, duration.
Messagethe sum of its calls — that is the figure at the foot of the answer, expandable by model.
Thread, user, dayaggregates over that, on the Cost page.
Repositoryindexing cost — embeddings only, because no generation call runs during indexing. Attributed to the repo instead of to a message.

Because the schema carries the model name per row, an additional or swapped model costs no migration — not even a later change of the embedding model in mid-operation.

Necessary, not optional

Prices come from litellm's model_prices_and_context_window.json, shipped along via //go:embed — an internal server should not reach out to the network to compute prices — with manual updates by the admin. The MiMo deployments are not public model ids and appear in no catalogue: a local model_prices override table keyed by deployment name is mandatory.

Phases

Every phase is its own feature branch off master and ends shippable. TDD throughout.

On scope, for the record

The recommendation was v1 = «how» plus «why», with «where to change» and spec conformance as specifications of their own. What was decided: all four in one specification — as written here. The practical consequence stands: eight phases fit into no single implementation plan, so every phase gets its own plan document at the handover. The specification is one; the plans are not.

Verification

  • make test (Go, -race) and make fe-test (Vitest), with coverage and diff-cover gates from peeq's hack/.
  • No test calls a real LLM, a real embedding endpoint or a real git remote: httptest fakes and a locally built fixture repository.
  • A migration that touches data → tested on a database brought up to the state of the previous migration.
  • End to end by hand: register a private repo → let it index → ask an ambiguous question → the clarification card appears → pick a candidate → the answer streams → open the source panel and actually look up a cited line → have it explained as Dev again and check that nothing is searched anew → the Cost page has moved.
  • Visible UI changes are driven with Playwright in the running app before they are reported as done.

Addendum phase 3: the routing level is measured and, for now, not built

Phase 3 was meant to produce module_profiles during indexing. Beforehand the thesis everything above it rests on was tested — scoring at module level improves the ordering — and without a single model call: group chunk hits by module and reorder by that. Six arms against the same 28 questions, the criterion fixed in advance. Result in docs/measurements/2026-08-17-module-ranking-and-comments.md: no arm beats plain chunk search (recall@5 0.679 against 0.607 in the best module arm, 0.214 in the worst).

Two causes, both visible in the data. Large modules win through their size: peeq/backend/internal/httpapi has 1135 chunks and buries a single very good hit under twenty mediocre ones. And the mild variant — a damped bonus instead of a regrouping — does help exactly the failure shape from phase 2 (rag/hybrid.go rank 7 → 2), but damages more questions than it repairs.

Plus a correction to this phase's rationale: the figure recall@20 = 0.857, from which «the answer is already there, just badly sorted» was derived, belongs to text-embedding-3-large. Under the -small actually used it is 0.786, so six of the 28 questions miss the top 20. Five of them are very much found — at fused ranks 23 to 52, three of them through the semantic lane. Only freebytes.go is not found at all. So it remains a sorting problem, and the module arms had the chance to solve it and did not take it.

Important for context: the measurement harness searches with the raw question. The design does not — step 1 «understand» produces expanded search terms including guessed code vocabulary, and per the «query side» section the query goes in twice, once in domain language and once in code vocabulary. That bridge is exactly what those six questions are missing: Apple TV → AirPlay, disk full → statfs. It is designed, unbuilt, and belongs to phase 4. Every number here therefore describes a configuration the design never proposed.

That is why module_profiles was not built at first — and after the decision further up, not at all. The routing level exists to raise answer quality; its cheapest precursor lowers it measurably, and 700–7000 Pro calls for the full version cannot be justified on that basis. What remains is the deterministic clustering: it costs nothing, and the Repos page counts with it. The follow-up question from the «path of a question» section needs a different source for its named candidates in phase 4 than precomputed profiles.

The counter-test stays open: the question catalogue has 28 entries and not a single genuine case of ambiguity — every question has exactly one correct repo and exactly one correct file. The value of a routing level lies precisely there. With a corpus where repositories overlap in their domain, the question has to be asked again.

Deliberately left open

  • Granularity of the module clustering — decided: the directory, with a folding rule below BACKEND_MODULE_MIN_CHUNKS and a splitting rule above BACKEND_MODULE_MAX_CHUNKS. On the real corpus 137 modules (peeq 52, loom 39, go-sqlite3 46). Two known weaknesses: a flat directory cannot be split (httpapi, 53 files on one level), and the selector does not skip dot directories, which is why .github/workflows shows up as a module.
  • A maintained or learned glossary for the vocabulary bridge — only if phase 4 shows that the found domain text plus expanded search terms fails on real questions.

Addendum phase 4b: routing happens, but asking has not earned anything yet

Phase 3's addendum left open where the follow-up question in phase 4 takes its named candidates from, if not from module_profiles. The answer: from per-turn naming over the deterministic module clusters. No profile is written during indexing; when the clarification card actually appears, every candidate gets a title and a one-line summary from its own top chunks, written by a non-Pro call. That is the other source demanded there — and cheaper than the discarded full version, because it only runs when the reader actually sees it.

repo_deps is now filled, from every go.mod in a repository's tree. It is the deterministic stage from «how rongo tells the two apart», separating composition from ambiguity without a model call.

The required measurement: non-Pro against Pro

The spec demanded exactly this number before writing anything in. Measured in docs/measurements/2026-08-18-routing.md, 61 questions:

One question of difference out of 61 — Pro finds one genuine ambiguity case more and is otherwise identical, including the same composition failure shape. That is no reason to lift the routing verdict onto the expensive deployment, and the spec's condition for writing non-Pro into routing is thereby met.

The uncomfortable result

A router that never asks reaches 0.803 on this catalogue — better than any configuration with a margin measured here, because 49 of the 61 questions do not want a follow-up question. At the default BACKEND_ROUTE_MARGIN = 0.25 the chain buys 16 wrong follow-up questions for 7 right ones and asks back on 8 of 44 questions that by definition have exactly one answer.

The fault does not lie in the verdict about the candidates, but in what the candidates are. Two repositories that both have a store package produce two candidates that look identical at the level the card shows.

The margin stays at 0.25

Not because 0.25 wins in the sweep table — it does not, 0.10 scores best. But because 0.10 only wins by asking less, and on a catalogue that is 80 % «do not ask» the metric rewards silence. Choosing the margin from that table would trim the router into switching itself off. The default stays until the candidate layer itself is fixed.

What routing does not damage

On the non-asking path the answer is still built from the complete result list. Citation fidelity over the questions the router did not ask back on is 0.944 (34/36) against the published 0.955 — one question of difference. Computed over all 44 unique questions it is only 0.773: a fifth of the unambiguous questions reach no answer at all on the first turn, because a follow-up question comes back instead.

composition unchanged at 0/5

As predicted in the phase 4b design before the code. repo_deps keeps the router from asking about them; it does not thereby make the questions answerable. The seam is sql.Open("sqlite3", …) plus a blank import — a string, not a symbol.

An old fault, now made visible

The manual test run shows a mix-up that phase 4b does not cause but does make visible. On the clarification card the reader picked the candidate peeq; for a statement about peeq the answer cited loom/backend/internal/auth/session.go:129-141 — although peeq has its own, byte-identical randomToken in session.go:135-141. The gatherer's reference walk (phase 4a) follows symbol names across repository boundaries; the spec's condition «the gathered code really references the symbol» is name-based, not resolution-based.

The mechanism pre-exists. The clarification card only turns it into a tangible problem, because it promises which mechanism was chosen — and the citation then points at code from the other one. That is a reproducible violation of «every statement is citable, and a citation points at the code the statement is actually about». It belongs to the candidate layer this addendum already leaves open for a later phase, not to this turn alone.

Open for a later phase

Two levers, both unused: candidate granularity — module identity may be as coarse as the already refuted module scoring from phase 3 — and the judge, which is never shown what would actually separate two candidates: Understanding.Repos is computed and does not appear in the prompt.

Addendum phase 4c: the judge moved to Pro, the candidate layer stayed unsolved

The second lever above was built and measured, twice, and did not earn its keep. What this phase brought instead came out of the measurement itself — details in docs/measurements/2026-08-19-candidates.md.

The measurement measured a different product

pipeline.go searches with Repos: u.Repos, the frozen expansions held only the search texts, and the routing arms searched without the restriction. Every published routing figure therefore came from a candidate set the product would never have produced. On top came the second case of the same family: the arms carried their own copy of the ladder. There is now exactly one ask.Decide, called by Route and by the measurement alike.

An invented repository name wiped out the search

Only freezing the restriction made it readable: of nine restrictions, three named something that does not exist — peeqs (the possessive), Peek and asg017/sqlite-vec. Such a name is not a restriction but a deletion: it goes straight into WHERE f.repo IN (…), nothing can match, and the turn reports «nothing found» about code that is in the index. Search now discards unknown names; a restriction with nothing left of it is no longer a restriction. A known but empty repository still restricts — «no hit means no hit» stays true.

The judge was rolling dice, and phase 4b's mandatory finding was an artefact

No call carried a temperature, so every gate call rolled with the endpoint's default. Two runs of the same arm over identical frozen inputs decided three of 61 questions differently — more than the difference phase 4b had measured between the two deployments and made the basis of a decision. The reader meets the same defect from the other side: the same question twice, once a card and once an answer.

Pinned with WithTemperature and run twice: Pro 48/61 and 50/61, non-Pro 42/61 and 43/61, residual spread one to two questions. The routing judge runs on Pro from now on — the one exception to «Pro only where a human reads», and it is written down as such in AGENTS.md. Its result is one word, but that word decides whether the reader gets an answer or a follow-up question. Understanding, naming and the thread title stay on the cheap lane.

The candidate layer: negative, and where the lever really sits

The judge was shown what separates the candidates — the repository named, the share of the hits including rank, and which expected identifiers landed where. In the loose version that halved the wrong follow-up questions (8 to 4) and lifted grounding to the best value ever measured, but cost the ambiguous cohort 7/12 to 4/12 and landed exactly on 0.803: it reached the router that never asks by becoming it. The strict version restored 7/12 and reproduced the baseline exactly. Neither is shipped; the judge prompt carries phase 4b's wording again.

What remains is the finding: the lever works — 8 wrong follow-up questions down to 4 is the largest movement ever measured on this cohort — and what is unsolved is the threshold, not the signal. The hit share probably does not belong in it: that the ranks sit close together is the reason the ladder reached the judge at all.

Finding B is fixed

The reference walk in gather.go now resolves a name in its own repository first and crosses the boundary only for a name that repository does not define at all. Genuine composition over repo_deps edges still travels. Checked against the running program, on the same path that produced the fault: card, peeq chosen, every hit in peeq, the word loom does not appear in the answer.

Open

Candidate granularity is still untouched. On the clarification card two of three candidates carried the same title — the naming prompt demands distinguishable titles and delivered none here; the card stays answerable because the repository sits next to it, but the titles carry nothing. And the composition cohort stays unanswerable for the reason named in phase 4b: the seam is a string, not a symbol.
