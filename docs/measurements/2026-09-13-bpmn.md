# A BPMN model is chunked by flow node, and the answer is told how it is wired

**Status: built 2026-09-13. `.bpmn` is a language; `symbols.ExtractBPMN`
emits one symbol per activity, gateway and named event, one per run of three
or more sequence flows, one for the diagram block; the chunker anchors on the
nodes and drops the diagram. `internal/bpmn` reads a model as a graph and the
answer prompt gets it as one line per node in walk order, for the models
among the sources and what they call. On a private estate's seven process
questions: text windows 12/26 and 15/26, flow-node chunks 17/26, chunks plus
the listing 19/26 and 21/26; cited parts 8/19 to 13/19. The trace question
went from 0/5 in five runs to 4/5 on the run where a model chunk was
retrieved at all.**

## Why

A private estate drives its claims processing from ten BPMN 2.0 models in a
workflow-engine repository (Operaton, Camunda 7's fork), plus three test
fixtures. rongo indexed them as plain text: no `LanguageOf` entry, so
600-token line windows, and half of every file is the `<bpmndi:>`
diagram-interchange block, shape coordinates and edge waypoints. On the
estate that was 151 chunks for 13 files, 76 of them carrying `dc:Bounds`.
A question about a task competed against its own coordinates.

Nothing here runs a model. The reader is an XML pass, re-run whenever the
file is, and what it stores is what the file says: the same rule as `edges`
and the declared-structure work.

## What was built

- `internal/symbols/bpmn.go`: `ExtractBPMN`. Namespace-agnostic on the local
  name (`bpmn:`, `camunda:`, `operaton:`, no prefix). One `Symbol` per task,
  call activity, sub-process, gateway and named event, `Kind` the element's
  local name, `Scope` the enclosing process id or sub-process name. Unnamed
  events are not symbols: an end event with an id and nothing else is a
  chunk of noise on its own and indexed anyway inside its neighbour's region.
- A run of three or more consecutive sequence flows is one `sequenceFlows`
  symbol. Modellers that write a node's flows right after it keep them in
  the node's region; modellers that collect every flow at the end of the
  process get a wiring chunk under the process instead of under whichever
  node came last. A run closes with its scope, and a listener under a flow's
  extension elements does not break it. Both were holes in the first draft.
- One `diagram` symbol at `<bpmndi:BPMNDiagram>`; `ChunkFile` skips that
  region. The symbol is stored so the viewer can say where the block is.
- Labels broken across the canvas with `&#10;` are collapsed to one line.
- `indexer.indexOne` dispatches on the language: ctags never sees a `.bpmn`.
- The fixture is a fictional order-intake model under `symbols/testdata`;
  the indexer's chunk test and the end-to-end index test read the same file.

On the estate after the change: 196 node chunks for 13 files, 0 with
coordinates, 206 symbols.

## Corpus

Seven German questions on the estate, three shapes: lookup ("which task
does X, and which code runs it"), one hop ("what happens when X fails"),
trace ("walk me through the process"). Two are cross-repository: the task's
delegate is an HTTP call into the backend, and the poll intervals are
process variables set from the backend's configuration. Rubrics were written
from the XML and the Java, not from an answer. The corpus is private
(`retrieve/eval/private/`, gitignored); the numbers are what is published.

Ran through `TestEvalMeasureAnswers`, audience BA, two runs per invocation.
The Pro lane flaked (stream idle, empty completion) on 6 of 28 step-1 turns,
so the step-1 numbers are one clean pair plus per-question rows from the
partial runs.

## What the trace question said after the chunking alone

Every run answered it from whichever node chunks retrieval returned, in the
order they came: a plausible paragraph per chunk, no sequence. The wiring
chunk was in the index, but a list of `sourceRef`/`targetRef` pairs is not
something the answer model orders into a walk, and nothing followed a
`calledElement` into the seven sub-process models.

## The process listing

`internal/bpmn.Parse` reads a model as a graph: nodes with their kind,
delegate, timer, error or signal, the node a boundary event hangs on, the
process a call activity runs; flows with their condition, default and
label; embedded sub-processes as scopes of their own. `Describe` renders
one line per node in walk order (breadth first from the start events, the
boundary events beside the node they interrupt), the outgoing branches on
the line. `Pipeline.describeProcesses` renders it per turn for every model
among the sources, then for the models their call activities run, one
level down, capped at 16k characters; it reads the files through the source
viewer at their indexed commit and stores nothing. The prompt block says
the listing gives the order and the branching, that every claim is still
cited from the node's own source, and that a called model with no source of
its own may be walked by name only.

Nothing here runs a model at index time; nothing is written to the
database. The definitions (error, signal, message names) resolve after the
walk because bpmn-js writes them after the process; `isExecutable` is not a
gate because it defaults to false; a call activity resolves inside its own
repository. Migration 0021 forces one re-index so an existing deployment's
models get their language and lose their coordinate chunks.

On the estate, the flagship model renders in 5.5k characters, all thirteen
in 26k; a trace turn carries the flagship plus its three called
sub-processes, about 12k.

The two one-hop questions about failure paths are where the listing pays:
the boundary event, the call activity it leads to and the branch conditions
are on one line each, and both answers now name all four rubric claims in
both runs. The trace question's 0/5 in run 1 is a retrieval miss, not a
listing miss: no model chunk was among the sources, so no listing was
rendered, and the answer walked the backend's job that starts the process
(status BEREIT, the scheduler, the engine call), which is true and not what
the rubric asks. Run 2 retrieved the model and walked it: parallel split,
patience mail, circuit breaker, receipt, validation, registration, the
poll-or-update branch, archiving, confirmation. The one absent claim is the
status poll's sub-process detail.

The polling question lost a point in run 2 to a contradiction the judge
found in a sentence about the default timeout. The listing shows the
timer as `${ereignismeldungstatusPollerTimeout}`, a variable, and the value
lives in the backend's configuration; whether that one is noise or a real
regression needs the next pair.

The edge kinds (`process` id joining the Java constant, delegate name
joining the interface method) were the other candidate after step 1. The
cross-repo questions already cite both sides, so those edges would be paid
for by questions that do not yet exist in the corpus. Not built.

## How to reproduce

The estate corpus is private. For the fixture: `go test ./internal/symbols/
./internal/indexer/ -run 'BPMN|bpmn'`. For an estate of your own: a
`repos.yaml` naming the workflow repository, `TestEvalIndex`, then
`TestEvalMeasureAnswers` with `BACKEND_EVAL_FLOW_QUESTIONS` and
`BACKEND_EVAL_RUBRICS` pointing at your questions, twice.
