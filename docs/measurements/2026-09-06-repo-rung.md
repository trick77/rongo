# The repository rung keeps its shape, and the judge cannot replace it

`2026-09-06-routing-rerun.md` attributed 16 of the ladder's 18 wrong decisions
to one rule: the repository rung fires on repository *span*
(`namedRepos == 0 && distinctRepos(all) >= 2`, `route.go`), with no test of
whether the second repository's candidate is worth offering. This arm asks what
that rung should do instead.

**Nothing ships.** No setting clears the criteria, and the two candidate
answers fail in opposite directions.

> **Superseded in part, 2026-09-06:** criterion 1 below is an accuracy target, and
> accuracy rewards a router that never asks. Priced apart, the shipping baseline is
> the cheapest setting in this document from W = 2 upward, and the tighter bars
> that cleared the accuracy baseline cost more than it does - `bar >= 0.80` costs
> 22.0 against the baseline's 20.0, buying 8 fewer cards with 5 more silently
> wrong answers. See `2026-09-06-routing-cost-metric.md`. The conclusion, that nothing
> ships, is unchanged and better supported.

## Criteria, fixed before the sweep ran

Written into the plan before any number landed, the way phase 4c fixed its
criteria and then declined to ship against them.

1. **Overall &ge; 52/65** - clears the *never ask* baseline (49/65) by at least
   three questions. The ladder has never cleared it; below that it is still not
   worth its cost.
2. **Ambiguous &ge; 12/16**, against 14/16 today. Trading more than two away is
   the old failure mode returning, whatever the aggregate does.
3. **Grounding on answered questions stays 1.000.**
4. Nothing clears all three: ship nothing, write it up.

Same pinned corpus as the re-run: rongo `0b989b6`, peeq `bb04021`, go-sqlite3
`3fa3f30`, index reproducing 526/5694, 142/1358, 293/2180, and the frozen
expansions unchanged.

## What the shape dump ruled out first

`TestEvalMeasureRepoRungShape` calls no model - `Rank` is pure over the hits -
and dumps the turns the rung actually decides. That population is **30**, not
the 46 that merely span: the ladder checks the manifest edge *before* the
repository rung, so 16 spanning turns are composed by `repo_deps` and never
reach it. Counting those in - as a first version of this arm did - measures a
set the rung does not decide, and inflates every "what would a bar buy" figure
roughly threefold. The 30 split 14 right and 16 wrong, which is exactly the
scored arm's rung breakdown, and that agreement is the check that the dump is
now looking at the right thing.

Two negatives, both worth having:

- **"Make the spanning candidate survive `worthOffering`" was already true.**
  `Ranked.All` is the filtered list (`route.go`), so the 0.4 relative floor runs
  *before* `distinctRepos` counts a second repository. The obvious remedy was
  already in force.
- **No scalar separates these turns.** The correct cards sit at second-repository
  score shares of 0.419 (error-text), 0.540 (listen-port), 0.613 (FuseWeighted),
  0.659 (proxy-header), 0.675 (chunk-texts) - in among the wrong ones, which run
  from 0.404 to 0.995. Hit count alone separates worse than score share.

## The sweep

`TestEvalMeasureRepoRungSweep`, over the whole ladder rather than the rung in
isolation. `Rank`, `Related` and `Judge` run at most once per question (49 judge
calls) and each setting is replayed with `ask.DecideWhySpans` - paying the judge
per setting would have mixed its own one-question re-roll into the comparison.
`Related` is paid twice per unnamed question on purpose: Route asks it over the
repository-grained list when the rung is live and over the capped module list
when it is not, so a setting that flips the rung flips which question was asked.

Two runs, because every setting that reaches the judge inherits its re-roll.
Run 1 asked the judge only the way Route asks it today, over the capped module
list; run 2 added the repository-grained question a real defer would ask.

| setting | overall (run 1 / run 2) | ambiguous (run 1 / run 2) |
|---|---|---|
| baseline | 47/65 / 47/65 | **14/16 / 14/16** |
| bar &ge; 0.50 | 47/65 / 47/65 | 13/16 / 13/16 |
| bar &ge; 0.60 | 46/65 / 46/65 | 12/16 / 12/16 |
| bar &ge; 0.70 | 47/65 / 47/65 | 9/16 / 9/16 |
| bar &ge; 0.80 | 50/65 / 50/65 | 9/16 / 9/16 |
| bar &ge; 0.85 | 50/65 / **51/65** | 7/16 / **8/16** |
| defer, modules | 49/65 / **51/65** | **0/16** / **2/16** |
| defer, repos | - / 45/65 | - / **2/16** |
| *never ask* | *49/65* | *0/16* |

The run-to-run spread is itself a result, and it lands exactly where
`2026-09-06-routing-rerun.md` said it would. **Every setting that never
consults the model reproduces to the question** - baseline and the 0.50 to 0.80
bars are identical across both runs. Every setting that does consult it moves by
one or two: `bar >= 0.85` by one, `defer, modules` by two. That is the pinned
judge's residual re-roll, measured a third time now, and it is why no reading
below rests on a difference of one or two questions.

## Finding 1: the judge as it stands today cannot do this rung's job - 0 of 16

Handing spanning turns to the judge instead of carding on span alone produces
**0.000 (0/16)** on the ambiguous cohort, and an overall score of 49/65 that is
*exactly* the never-ask baseline. That is not a coincidence: the judge composed
every single cross-repository ambiguity, so the ladder stopped asking anything
the rung used to ask.

The first run only asked the judge the way Route asks it today, over the capped
module list, and that left an obvious objection: the judge's user message prints
`Repository %s, module %s` per candidate (`route.go`), so on a module list the
top rows can name the *same* repository twice and the cross-repository ambiguity
never reaches the model at all. A real defer would pass
`RepoCandidates(ranked.All)`, one entry per repository.

**Measured, and it does not rescue it.** Showing the judge one candidate per
repository gives **2/16** on the ambiguous cohort - the same as the module list
to within the judge's own re-roll - and 45/65 overall, six questions *worse*.
Naming the repositories does not make the model card them; it only costs the
composition and comparison questions that the module list happened to get right.
So the finding is about the judge on either input, not about a prompt that had
not been tried.

What is measured is still worth stating plainly, because it corrects the reading
the re-run invited. The re-run showed the judge owning zero wrong decisions
against the repository rung's sixteen, which reads as "the model is better than
the rule". On the evidence here it is not that simple: the judge is right about
modules inside one repository and, on the input it is given today, wrong about
the same mechanism in two repositories every single time. The rule knows the
repository names. The model, as fed, does not.

## Finding 2: the bar's aggregate gain is bought by asking less

`bar >= 0.80` is the first setting ever recorded that clears *never ask* -
50/65 against 49/65. It gets there by dropping the ambiguous cohort from 14/16
to 9/16. `bar >= 0.85` scores the same overall and takes ambiguous to 7/16.

That is the criteria doing their job. The aggregate rewards silence: 49 of the
65 questions want no card, so a ladder that asks less scores better while
serving the reader worse on exactly the questions the card exists for. Criterion
2 is what stops the sweep from optimising into a router that never asks -
which, on this catalogue, would score 0.754 and be useless.

Only `bar >= 0.50` and `bar >= 0.60` hold the ambiguous cohort near baseline,
and they move the overall number by at most one question, in the wrong
direction at 0.60.

## Finding 3: what the rung's 16 failures actually are

The bar removes them slowly - 16, 15, 15, 11, 8, 6 as it tightens - and every
question it removes costs roughly one ambiguous question somewhere else. So the
false cards are not a tail of weak second repositories that a threshold can
shave off.

What the dump supports, and no more: over the 30 turns the rung decides, the
score-share and hit-count distributions of the right and wrong cards overlap
almost completely - 0.404 to 0.995 on one axis, 1 to 10 on the other, with a
correct card at 0.419 and a wrong one at 0.404, a correct one at 0.993 and a
wrong one at 0.995. Whatever separates a genuine cross-repository ambiguity from
a peeq-only question that pulled a rongo chunk into the fused twenty is **not in
either signal**.

Every one of the 30 is peeq against rongo; go-sqlite3 never appears as the
second repository. That is the corpus working as designed - peeq and rongo were
chosen to overlap only where they have to - and it also means this whole finding
is about one repository pair, on a catalogue built to make that pair hard.

What the stray chunks actually *are* was not examined. The dump now prints both
repository names, but why a rongo chunk ranks second on "In which format does
yt-dlp expect the cookie file?" is a question for a run that reads the chunks,
not one that reads their scores.

## Conclusion

The rung stays as it is. Two candidate replacements were measured against
criteria fixed in advance and neither qualified: the bar trades the ambiguous
cohort for an aggregate that rewards silence, and the judge collapses it
entirely.

What ships from this run is the measurement apparatus, not a behaviour change:
the shape dump, the sweep, and `decideWhy` taking the repository rung as a
parameter so the question can be re-asked without rewriting the ladder.

Both obvious answers are now closed, on their own best inputs. What is left for
a future attempt is a signal that is neither a score, a count, nor the judge's
verdict: *which repository* the hits come from and whether the question's own
language belongs to one of them. "In which format does yt-dlp expect the cookie
file?" is a peeq question in its wording, and no threshold on the fused scores
knows that.

The prior on that is bad, and it should be stated with the hypothesis rather
than discovered again: phase 4c showed the judge more evidence - the repository
named, each candidate's hit share, which expected identifiers landed where -
measured it twice, and could not show it earning its keep
(`2026-08-19-candidates.md`). This run adds that naming the repositories in the
candidate list does not help either. So the next attempt needs a design and a
reason to believe, not another knob.

Worth keeping in view: the rung is wrong 16 times out of 65 and the ladder as a
whole sits two questions under *never ask*. That is a real cost, and it is also
small enough that shipping a change which trades five ambiguous questions for
three aggregate ones would be the worse outcome. Leaving it alone is a decision,
not a deferral.
